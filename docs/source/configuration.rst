Configuration
=============

Quick start
-----------

GRS needs two radiative transfer look-up tables (LUTs), ``toa_lut_opac_wind_v3.nc`` (835 MB) and
``transmittance_lut_opac_wind_v3.nc`` (0.6 MB), shared with hGRS and published on Zenodo
(`doi:10.5281/zenodo.23394202 <https://doi.org/10.5281/zenodo.23394202>`__). Either:

- **download them into the default folder**, with no configuration: ``~/.local/share/grs/lut`` on Linux
  (``~/Library/Application Support/grs/lut`` on macOS, ``%LOCALAPPDATA%\grs\lut`` on Windows):

  .. code-block:: bash

     grs_config --download

- **or keep them in another folder** (e.g. a copy shared with hGRS or with other users) and write it in
  your user configuration file:

  .. code-block:: bash

     grs_config --init /path/to/lut    # creates ~/.config/grs/config.yml
     grs_config --download             # if the LUTs are not there yet

Then check:

.. code-block:: bash

   grs_config                          # prints the configuration in use and checks the LUTs

Nothing else is needed: all the other settings have default values. The configuration is read at run
time, so it can be changed without reinstalling the package.

``grs_config`` gives the LUT folder in use and where it is set (``GRS_DATA_ROOT``, user configuration
or default folder), and ends with the status of each LUT; it returns the exit code 1 if one is missing::

   LUT folder:            /path/to/lut (user configuration)
   ...
   LUT toa           ok      /path/to/lut/toa_lut_opac_wind_v3.nc
   LUT transmittance ok      /path/to/lut/transmittance_lut_opac_wind_v3.nc

The processing also checks the LUTs before reading the image, and stops with a message giving the
missing files.

Download of the LUTs
--------------------

``grs_config --download`` downloads the LUTs missing from the LUT folder from the Zenodo record set
in the ``zenodo`` section of the configuration; ``--force`` downloads them again. Each file is checked
against the MD5 checksum given by Zenodo and written to a ``.part`` file renamed at the end, so that an
interrupted download never leaves an incomplete LUT. In Python:

.. code-block:: python

   from grs.config import download_luts

   download_luts()

The LUTs can also be downloaded from the `Zenodo web page <https://doi.org/10.5281/zenodo.23394202>`__
and copied into the LUT folder by hand.

Where the settings come from
----------------------------

The settings are merged from, in increasing order of priority:

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - Source
     - Content
   * - Packaged defaults, ``grs/config.yml``
     - All the settings (see `Settings`_ below). Do not edit this file: it is replaced when the package
       is reinstalled.
   * - User configuration file, ``~/.config/grs/config.yml``
     - Only the keys to change, with their parent keys. Its location is
       ``$XDG_CONFIG_HOME/grs/config.yml`` if ``XDG_CONFIG_HOME`` is set, or the file given by the
       ``GRS_CONFIG`` environment variable.
   * - ``GRS_DATA_ROOT`` environment variable
     - Folder of the LUTs (``path: grsdata``).

When ``grsdata`` is set nowhere (``null`` in the defaults), the LUTs are read from the default folder
(:py:func:`grs.config.default_data_root`). This suits a personal installation; on a shared machine or
a cluster, set ``GRS_DATA_ROOT`` (e.g. in the module or job environment) to a shared copy of the LUTs.

``grs_config --init /path/to/lut`` writes the user file with the folder of the LUTs and, commented, a
copy of all the default settings: to change one, uncomment it with its parent keys. Without a folder,
``grs_config --init`` leaves ``grsdata`` unset and creates the default folder. It does not overwrite an
existing file, unless ``--force`` is given.

Environment variables
~~~~~~~~~~~~~~~~~~~~~

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Variable
     - Effect
   * - ``GRS_CONFIG``
     - Path of the user configuration file to use instead of ``~/.config/grs/config.yml``
       (error if the file does not exist).
   * - ``GRS_DATA_ROOT``
     - Folder of the LUTs; takes priority over ``grsdata`` in any file.

Examples
--------

Use a shared copy of the LUTs and another CAMS folder, in ``~/.config/grs/config.yml``:

.. code-block:: yaml

   path:
     grsdata: '/work/datalake/watcal/GRS/grsdata_v21'
     cams: '/work/datalake/watcal/cams'

Run a batch with its own settings, without changing your user file: write the settings of the batch
in a file and give it with ``GRS_CONFIG``:

.. code-block:: bash

   export GRS_CONFIG=/path/to/batch_config.yml
   grs_config                          # check
   xargs -P 2 -I{} bash -c '{}' < grs_commands.txt

In Python, the configuration in use is given by :py:func:`grs.config.load_config`; the LUT files of a
:py:class:`~grs.grs_process.Process` can also be set directly:

.. code-block:: python

   from grs.config import load_config
   import grs

   load_config()['path']['grsdata']

   process = grs.Process()
   process.lut_file = '/path/to/toa_lut_opac_wind_v3.nc'

The configuration is read once per session (cached): after changing the user file or the environment
variables in a running notebook, call ``load_config.cache_clear()``.

Troubleshooting
---------------

``LUT file(s) not found``
   The LUTs are not in the folder in use: run ``grs_config`` to see this folder and where it is set,
   then download them with ``grs_config --download``, or set the right folder with
   ``grs_config --init /path/to/lut --force`` (or edit ``grsdata`` in the user file). A
   ``GRS_DATA_ROOT`` variable set in your shell takes priority over the file.

``no Zenodo record of the LUTs is configured``
   The ``zenodo: record`` setting is empty: download the LUTs from the Zenodo web page and copy them
   into the LUT folder, or set the record in your user file.

``checksum mismatch``
   The download was corrupted (the incomplete file is removed): run ``grs_config --download`` again.

``GRS_CONFIG points to a missing file``
   Unset ``GRS_CONFIG`` or correct the path.

The settings seem ignored
   Check with ``grs_config`` which user file is read (``found`` / ``not found``) and the merged
   configuration; the YAML indentation decides the section of each key.
